# Подключение APlayer к Playback Engines

Проверено 23 ноября 2026 на Raspberry Pi 4, Volumio 4.239, ARMHF.
Звук писал `arecord` с выделенной карты `snd-aloop`. Все аудиотесты запускали
полноценный `aplayer`, кроме явно указанного теста отдельной программы `ap`.
Изменения пока ограничены исследованием и временными пробами.

## Версия и интерфейсы

- Официальный ARM32-архив и запущенный HTTP-интерфейс показывают **2.21**.
  SHA-256 архива `030ff12da35d07be4842959ae6bce9b2e271777849afb59d14e1e80590c41397`.
  В [истории релизов](https://albumplayer.ru/linux/updates.txt) последняя версия
  датирована 15 ноября. Для 2.20 уже есть [контрольная запись PCM](../testing/native-ap-cue-contract.md).
  Ни одна из двух версий не прошла тест произвольного порядка из AP3 с диапазонами CUE.
  Отдельный 64-битный бинарник потребует 64-битного ядра, а на этой Pi сейчас `armv7l`.
  [Загрузки автора](https://albumplayer.ru/linux/english.html).
- Полноценный `aplayer` поставляется как исполняемый файл с HTTP-интерфейсом и штатным unit типа
  `forking`. В опубликованных пакетах SDK для загрузки движка внутрь Node.js не найден.
  `ap2gui` и `ap2con` управляют тем же процессом. Проверка исходников `ap2con`
  подтвердила использование команд того же HTTP API. [Описание ap2con](https://albumplayer.ru/ap2gui/readme_ap2con.txt).
- В штатном интерфейсе есть выбор папки, замена списка, добавление альбомов, удаление альбомов,
  сохранение .ap2, команды транспорта и состояние. Плейлист .m3u в каталоге плеера
  не появился в `GetPlaylists`. Команды остановки на произвольной границе трека
  в HTTP-интерфейсе и настройках не найдено.
- Отдельный консольный `ap` 1.05 на Pi по команде `1.2` начал WAV с второго
  CUE-трека и вывел второй **и третий**, по 44 100 кадров. Терминальное управление
  даёт выбор старта и позиционирование, но тест границы исключает его как решение
  для произвольной очереди. [Руководство, раздел 8](https://albumplayer.ru/linux/album_player_linux_manual_ru.pdf).

## Проверенные способы управления

| Вариант | Результат |
| --- | --- |
| Штатная очередь по исходному CUE | Альбом играет последовательно. `auto_mode=false` действует между альбомами. |
| Записать произвольный порядок в AP3 | Для первого трека с объявленной длительностью 1 с записано 132 300 кадров всего трёхсекундного файла при всех пяти комбинациях Standard, Direct Input, Full Memory и gapless. Для среднего трека получалось 132 300 или 88 200 кадров вместо 44 100. Путь AP3 содержит старт, например `data.wav?1000`. Объявленная длительность и состояние API не задают жёсткий конец. |
| Синтезировать CUE для выбранного диапазона | Следующий `TRACK … MODE1/2352` сыграл как аудио, `POSTGAP` оставил полный файл, а отсутствующий следующий файл не остановил воспроизведение перед соседними кадрами. |
| Очередь снаружи, один обычный файл за раз | Плеер перечитал один выделенный каталог при каждом выборе, даже при повторе того же источника. Проверялись `State.Scanning=false`, один трек и точный путь из `GetPath`. Переход после естественного EOF прошёл с произвольным порядком. |
| Отдельный процесс по требованию | Приложение запустило ARM32 `aplayer` от непривилегированного пользователя, дождалось API и завершило процесс. Отдельный тест с transient systemd unit подтвердил `Type=forking`, `PrivateNetwork=yes`, получение `/?State` через Unix-сокет режима 0600 и завершение реального MainPID через systemd. Порт 7778 в сети хоста отсутствовал. |

## Результат очереди, которая подаёт один файл за раз

- **CUE с PCM-источником.** Существующий [подготовщик CUE](../../playback-engines/lib/cue-stream.js)
  создал два WAV с точными границами. Изолированный `aplayer` воспроизвёл
  `3 → 1 → 3`. Во всех трёх записях ровно 44 100 кадров нужного маркера,
  каналы совпадают, чужих ненулевых кадров нет. WAV подан как локальный файл,
  после подготовки движок сам декодирует и выводит звук.
- **FLAC.** Один обычный файл напрямую со своего пути. Получены подряд
  три маркера по 44 100 кадров и EOF.
- **DSF/DFF.** Оригинальные DSD64-файлы через симлинки. Сняты DoP кадры
  S32_LE/176,4 кГц, маркеры 0x05/0xFA присутствовали в равном количестве.
  У DSF проверены пауза, перемотка на 50%, продолжение и EOF. DFF проигран
  до EOF целиком. В режиме Native DSD для обоих контейнеров ALSA показала
  DSD_U32_BE/88,2 кГц. В секундной записи по 705 600 байт содержался заданный
  DSD-маркер, а в начале каждого захвата было немного тишины 0x69.
- **Отдельный трек SACD ISO.** Из [образа CC0](https://github.com/aclater/sacdfs/blob/main/tests/corpus/images/dsd-stereo-mch-2048.iso)
  извлечены только стереотреки 1 и 3 в DSF без перевода в PCM. Сборки на x64 и
  на Pi дали одинаковые SHA-256 для каждого файла. На Pi для теста
  [netXing/sacd_extract](https://github.com/netxing/sacd_extract/tree/63e5231)
  собран с заменой x86-специфичных функций выравнивания на `posix_memalign/free`.
  Сборка [EuFlo](https://github.com/EuFlo/sacd-ripper/tree/c9af7d4) отвергла
  этот синтетический образ по проверке таблиц TOC. Воспроизведение извлечённых
  DSF самим `aplayer` в PCM дало `Gamma → Alpha → Gamma`: 1029, 1323, 1029
  ненулевых кадров с одинаковым SHA-256 для обоих прогонов Gamma. Это короткая
  фикстура. DST, многоканальные образы, gapless для ISO и штатная упаковка
  экстрактора для Volumio требуют отдельной проверки. При прямой подаче ISO
  штатный каталог APlayer работает, а точное ограничение произвольной записи
  в AP3 пока не подтверждено. [Предыдущая проверка ISO](../testing/2026-11-23-cue-dsd-on-raspberry-pi.md).
- **Одна папка со всей подготовленной очередью.** Три WAV с именами `001–003`
  штатно загрузились в `aplayer`. С выключенным gapless получили точный порядок
  `3 → 1 → 3` по 44 100 кадров, и на симлинках, и на отдельных копиях.
  С включённым gapless в обоих случаях PCM содержал `1 → 3`: 88 200 кадров
  маркера 1, затем 44 100 маркера 3, хотя HTTP сообщал три перехода. Такой список
  годится для фиксированной подборки при проверенной конфигурации. Для живых
  изменений пришлось бы поддерживать ещё и актуальность снимка очереди в APlayer.

## Как подключать

1. Очередь и её ревизия остаются в Volumio. Локальный адаптер подаёт в
   `aplayer` один файл, ждёт подтверждения выбранного пути и продвигает очередь
   по EOF активной записи. Pause, seek и stop идут через HTTP API. При Next
   и редактировании поздние события предыдущей записи нужно игнорировать.
2. По первому локальному запросу запустить отдельный сервис `aplayer` с
   приватной сетью и доступом к HTTP через защищённый Unix-сокет. Каталог
   запуска и ALSA-конфиг отдельные. При передаче ЦАПа другому движку остановить
   локальный вывод и освободить устройство. Такой запуск проверен на Pi.
3. Подавать напрямую FLAC, WAV, DSF и DFF. Для CUE по PCM-источнику явно
   готовить ограниченный локальный WAV существующим кодом. Для произвольного
   SACD-трека рассматривать извлечение в DSF после выбора экстрактора и
   проверки реального SACD/DST. Полный альбом по исходному CUE или ISO возможен
   в штатной альбомной очереди.
4. Текущий интернет-транспорт остаётся на `ap2renderer`. Это сохраняет
   контроль конечных HTTP-треков для Qobuz и Яндекс Музыки. Автор поставляет
   для этих сервисов отдельные приложения со своими интерфейсами и очередями.
   В пробе с Radio Mode `aplayer` принял локальный HTTP URL и заиграл FLAC,
   но сообщил длительность 35 999 999 мс для файла длиной 3 с.
   Seek на 50% сдвинул только состояние, новых запросов Range не было.
   [История релизов](https://albumplayer.ru/linux/updates.txt).

Перед включением в Playback Engines отдельно проверить pause/seek/stop
и замену очереди через настоящую state machine Volumio, переходы между разными
форматами, очень короткий трек, совместный доступ к ЦАПу и работу через FiiO.
Текущий результат подтверждает корректный вывод и EOF в исследовательском
контроллере. Для стандартного интеграционного режима важно явно указать, что
разрезание CUE подтверждено для PCM, а бесшовные переходы для внешней очереди
ещё не проверены.
